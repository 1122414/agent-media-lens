# AgentMediaLens 与本地 BiliNote 的同链接实测

2026-11-18，用同一个 Agent 从抖音和 B 站链接读取真实画面与口播，全程通过 MCP、HTTP 和本地文件，没有操作网站播放器。复用[上一轮的三个公开链接、五个固定时刻和原片参照](2026-11-18_agent-video-comparison.md)。本轮已知答案，是复测。画面须与目标秒原片相符且有实际图片。识别文本与同期字幕、歌词画面分别核对，没有人工逐字听写。

## 运行条件

- AgentMediaLens 0.5.0 使用已配置的 Evil0ctal 访客读取服务，另起三个任务，沿用每条最多 30 帧、基础间隔 4 秒、处理后清理原片的设置。Agent 通过 `media_get_frame(timestamp)` 接收 JPEG 及其实际帧时间，通过 `media_get_transcript(start,end)` 读取覆盖查询时刻的识别段。
- BiliNote 使用作者发布的 ARM64 一体化镜像 2.4.5，镜像摘要 `sha256:0c1e996949640a4b95e44c19d2d5ebd5051a8d48cd60bc4fa967e3228ce4d6a3`。在空 Cookie 的本地服务提交原链接，不向它提供 AgentMediaLens 的媒体、帧或转写。B 站没有可用平台字幕，两边都用本地 Whisper base 识别。BiliNote 的笔记与聊天使用本地 Qwen3-VL-2B-Instruct Q8_0。首次拉取备用镜像时 Docker 虚拟盘写满，回收失败下载后重新提交了全部链接。CPU 推理的一次聊天遇到 VM 内存上限，随后使用同一权重切换到宿主机 llama.cpp b12498 与 Metal，重做了问答。环境故障均未计入能力评分。
- BiliNote 使用 `POST /api/generate_note`，质量选 medium，开启截图、原片回链与多模态理解，使用界面默认的 6 秒采样、2×2 网格。Agent 轮询 `GET /api/task_status/{id}`，读取笔记及转写，并请求笔记里的静态图片。普通笔记请求没有给出任何目标秒或参考答案。另测 `POST /api/chat/ask`，以及在新笔记中通过补充要求指定截图时刻。实际运行的 OpenAPI 共列出 29 条路径，生成笔记要求提供模型及供应商，未列出接收任意时间点并返回图片的独立路由。[笔记路由](https://github.com/JefferyHcool/BiliNote/blob/be3889395afb5346aa4339ae933d3ba2e08f25a8/backend/app/routers/note.py) · [聊天工具定义](https://github.com/JefferyHcool/BiliNote/blob/be3889395afb5346aa4339ae933d3ba2e08f25a8/backend/app/services/chat_tools.py)

AgentMediaLens 直接查帧 3/5，对两次未命中均能读到返回帧的实际时间。BiliNote 的抖音两条链接覆盖三个时间点，均未获得可评分画面。B 站的内部采样包含 216 秒的黄锁帧，第 32 秒处只有 30、36 秒附近样本。30 秒图上尚未显示 4,898。内部采样仅作为诊断，不能直接计作普通接口交付。

额外调用 BiliNote 自带的 `generate_screenshot`，对它自己读取的 B 站视频指定 32、216 秒，将图片通过本地 HTTP 取回并查看，分别读到了 4,898 和黄锁。这个检查验证了 BiliNote 准确取帧的底层能力。调用方需要容器文件访问权限和媒体路径。[截图函数](https://github.com/JefferyHcool/BiliNote/blob/be3889395afb5346aa4339ae933d3ba2e08f25a8/backend/app/utils/video_helper.py)

## BiliNote 的公开接口能否给出精确截图

**能。** 向 `/api/generate_note` 提交同一 B 站链接，在 `extras` 里要求保留 `*Screenshot-[00:32]` 和 `*Screenshot-[03:36]`，没有提供数字、画面或答案。沿用 6 秒采样、2×2 网格、简洁风格，只勾选截图。复用的是 BiliNote 第一次从该链接生成的 306 段转写。服务返回两条静态 JPEG 链接，Agent 通过 HTTP 取回，分别看清了 4,898 和黄锁。两幅图的文件内容逐字节匹配单独按同一秒解码生成的 BiliNote JPEG。第 32 秒即便不在六秒网格上，也能通过新笔记生成准确的原片截图。

定点笔记的两段配文都泛谈操作账号或执行任务，未说出 4,898 或「配对只要一次」。Agent 读取图片和原始转写才能核实这些细节。对已有普通笔记调用 `/api/chat/ask`，实问 32 秒时模型复述了「快五千顆星」，未给出 4,898。实问 216 秒时它把前面关于开发者身份的讲解当作当前画面和口播，未答出黄锁或当句台词。两次聊天响应都有文字，没有图片载荷。运行中的工具定义支持查询转写、笔记和视频元信息。

首次 CPU 普通笔记打开了回链与截图，模型连续输出 `Content` 标记，触及本次 CPU 推理服务的 1,400 token 上限。该笔记含完整转写，没有 PNG/JPEG 引用。取消此人为输出上限后，改以宿主机 Metal 和界面默认的简洁风格、仅勾选截图复测。普通笔记与定点笔记并发时发生过共用中间目录缺帧，普通笔记已单独重跑。定点笔记和后续问答均未使用 CPU 的 1,400 token 上限。

单独重跑的普通笔记没有预告目标秒。模型输出了 1,693 个不同的截图时刻，最晚到 28:15，原片长 7:12.45。逐一请求成品笔记的图片 URL，430 个返回 HTTP 200，1,263 个返回 HTTP 404。404 全部对应片长外的时刻。32 秒和 216 秒都在可用的图片里，两张 JPEG 均与精确取帧结果相同。这份笔记的聊天请求超过 82,700 token，在 24,576 token 上下文设置下两次均被模型拒绝。指定只取两张图的新笔记没有出现这种情况。上述数量来自这条视频与所选的 2B 模型。

用相同权重临时将上下文扩大到 98,304 token 后，对同一普通笔记重复原问题，两次聊天均正常返回。32 秒答出字幕约数，却加入了后面才出现的自我介绍，漏掉星数 4,898。216 秒正确读出「配对只要一次」，把「钥匙是他自己……」错列为同期口播，未指出黄色锁。扩大上下文解决了请求长度问题，仍需外部 Agent 看真实帧、按区间读原始转写来核对回答。

再对已附上两张准确图片的定点笔记发起聊天。32 秒的回答复述「快五千顆星」，随后将后面的自我介绍当作该秒口播。216 秒的回答给出了画面字幕「配對只要一次」，却把更靠后的钥匙说明当作口播。两次响应都没有返回图片。对同一个外部 Agent 来说，这两题可以通过取回图片并读取笔记结果里的原始转写答对。

## 宣传边界

| ID / 优先级 | 观察及当前行为 | 可采取的做法与预期 | 风险与代价 | 状态 |
|---|---|---|---|---|
| V1 / 高 | AgentMediaLens 在 00:32 给了 00:39 的画面，BiliNote 明确指定 00:32 新建笔记可以给出准确图片 | 宣传时演示 Agent 读取帧 ID、实际帧时间和转写。产品若要承诺任意秒，补充可按需取帧的入口，用 4,898 验收 | 跳过时间核对会答成下一镜。重新读取媒体有延迟和可用性成本 | 时间偏差与竞品定点取图均已实测 |
| A1 / 中 | B 站同两句口播在两款工具中时间和内容相同。抖音歌曲的真实帧能读出正确歌词，AgentMediaLens 的转写仍有同音错字 | 对话示例分别写明「画面上写了什么」和「识别段里说了什么」 | 把画面文字当成录音原话会高估准确率。复核需要读取图片和对应段 | 已按两个模态核对 |
| D1 / 中 | 已配置的 AgentMediaLens 在三条链接都返回图文证据。BiliNote 空 Cookie 实例读通 B 站，两条抖音均未读通 | 对外表述为已配置访客服务的公开链接能力。保留平台、时间、样本范围 | 把两条失败推广为平台永久不支持，会误导使用其他配置的用户 | 本机实测，跨配置原因未定 |
| N1 / 中 | BiliNote 的普通配图笔记产生超片长的截图标记，成品保留了 1,263 个无图地址。定点笔记则准确交付两图 | 评测普通笔记时逐一核对 HTTP 状态，对目标图片校验实际内容。生成失败与模型选错时刻分别记录 | 只统计 Markdown 中的图片数量会高估交付量。逐张核验增加本地读取时间 | 已检查两份成品的全部图片引用 |
| N2 / 中 | 同片笔记并发时，普通笔记在读取共用帧文件时收到 `FileNotFoundError` | 独立任务串行重跑，使用成功落盘的结果计分 | 并发时的临时文件冲突可能掩盖真实能力。串行需要更长等待 | 一次并发失败，串行复测成功 |

复查这台机器上的服务可访问 [本地 BiliNote](http://127.0.0.1:18763/)。Web 端和后端在同一容器，模型在宿主机回环地址运行，权重保存在项目的忽略缓存目录。若手动停止两项服务，可在项目根目录运行 `.cache/bilinote-local-2.4.5-wvqu/start.sh` 恢复。仓库只收录复测方法和观察结果。
