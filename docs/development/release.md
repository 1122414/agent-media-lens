# Release procedure

Use the version already agreed for the release in package.json, the Python project and lockfile, and the plugin manifest. CLI and MCP read the package version. Keep previous release reports historical. Update the changelog and add docs/releases/vX.Y.Z.md with measured acceptance and limits.

Run the local checks in [testing](testing.md), test a clean checkout with Docker and a stdio client, and inspect the public demo for secrets, private paths and third-party material. Package the exact candidate with `sh scripts/package-release.sh X.Y.Z /tmp/unique-output HEAD`. Extract both archives into fresh directories, verify the launchers and marketplace's relative paths, and verify SHA256SUMS. The source bundle includes the runtime build recipe; the marketplace bundle alone does not. No compiled codecs, ASR models or provider identities ship. Review dependency licenses and notices before changing the distribution format, particularly when shipping a compiled [FFmpeg build](https://ffmpeg.org/legal.html).

Push main and require successful CI on that exact commit (Node 24, Node 26 and container). Tag it without rewriting existing tags. The release workflow verifies CI, notes and manifest, builds both archives, attaches the demo and checksums, and publishes. Read the release back, download the assets and verify their checksums. Local marketplace support does not imply an official directory listing.
